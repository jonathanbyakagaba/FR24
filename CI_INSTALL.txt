Installing the FR24 automation - two routes, both browser only. Pick one.

    ROUTE A needs a terminal for six commands. ROUTE B needs no terminal at all: you upload one file,
    paste the text of another, and press two buttons. If Codespaces is not where you expect it, do B.

ROUTE A - Codespaces (why: `gh` and `git` in there are already signed in as you)

    Where it is: open the repository page and press the green **Code** button -> **Codespaces** tab ->
    **Create a new codespace**. Or skip the hunting and open github.com/codespaces/new?repo=1220000000
    - the short form is **https://codespaces.new/jonathanbyakagaba/FR24**.
    If there is no Codespaces tab at all, it is switched off for the account: github.com/settings/codespaces
    -> enable it. Note codespaces.new and github.dev look alike: **github.dev (the `.` key) has no
    terminal you can use for this** - you want the one that says "codespace".

0.  Once, either route: FR24 -> Settings -> Actions -> General -> scroll to **Workflow permissions**
    -> **Read and write permissions** -> Save. Without it the runner cannot push and every run fails
    at the commit step with "Resource not accessible by integration".

1.  github.com/jonathanbyakagaba/FR24 -> Code -> Codespaces -> Create codespace on main
    (Codespaces is free on a public repo, and `gh` there is already signed in as you: that is the
    whole reason to use it instead of fighting for a token.)
2.  Download ci_install.tar.gz from the Arena workspace, then drag it onto the Codespaces FILES
    panel. It lands in /home/codespace/. or in the repo folder - either is fine.
3.  In the Codespaces terminal:

      tar xzf ~/ci_install.tar.gz -C /workspaces/FR24 2>/dev/null || \
      tar xzf ci_install.tar.gz -C /workspaces/FR24
      cd /workspaces/FR24
      git add -A && git status --short | head        # expect tools/, .github/, work/, .gitignore
      git commit -m "Add the FR24 build: tools/, work/*.py, fr24-nightly workflow"
      git push

4.  Actions tab -> "fr24-nightly" -> Run workflow -> check  skip_fetch  -> Run workflow.
    A pushed workflow file is already scheduled; if the Actions page instead offers
    "Set up schedule", click it. The schedule is 04:10Z and 16:10Z daily.
5.  Open that run and read the "Build summary" step: 16 lines of ok / SKIPPED, then "files this run
    published". The run commits by itself.
6.  Codespaces (github.com/codespaces) -> delete the codespace when you are done.

ROUTE B - no terminal, five minutes, all buttons

1.  Do step 0 above.
2.  FR24 -> Add file -> **Upload files** -> drag `ci_install.tar.gz` in -> Commit changes. Root of the
    repository, not inside any folder.
3.  FR24 -> Add file -> **Create new file**. In the "Commit new file" box, click into the **name field**
    (it says "Commit new file") and type exactly:  .github/workflows/00-install.yml
    GitHub creates the folders as you type the slashes. Paste the body of `00-install.yml` from the
    Arena workspace into the editor, then Commit changes **to main**.
4.  FR24 -> Actions -> **00-install-the-build** -> Run workflow -> Run workflow. It unpacks the bundle,
    commits tools/, work/, reference/, metar/, .gitignore and the nightly workflow, and deletes the
    tarball. Green means installed.
5.  FR24 -> Actions -> **fr24-nightly** -> Run workflow -> tick **skip_fetch** -> Run workflow. Read
    its Build summary. From here on the 04:10Z / 16:10Z schedule does it by itself.
6.  Optional tidying: delete `.github/workflows/00-install.yml` (open it -> pencil -> trash) so the
    list of workflows only holds the nightly one. It is harmless if you leave it; nothing schedules it.

What step 4 does, and why it is the safe first run
    skip_fetch means "do not ask Flightradar24 for anything": the build ingests FR data.zip as it
    already sits on main and rewrites the derived tables from it. Your archive on main is NEWER than
    the one in this Arena workspace (1,108 tracks and October through 18 Oct, vs 1,001 and through
    15 Oct), and the Arena cleaner repairs it on the way in - measured with --check, nothing written:
    1,108 entries -> 1,107 tracks, 1 row-identical copy removed, and UR110-3ed2932d.csv restored to
    1,065 rows where the uploaded archive carried only 234. So the first run moves the tables toward
    the archive, not toward the older workspace.
    Paths that both builders write - manifest.csv, flights.csv, runway_usage.csv, fleet_summary.csv,
    triangle_assignments.csv, date_coverage.md, all_flights_aeroroutes.md, no_code_tracks.md - end up
    with Arena's convention (one row per leg). notams.csv, od_matrix_*, <month>/metar/ and the FTA
    files are never written by it, so they stay.

After that it is automatic
    Twice a day: fetch -> ingest -> rebuild every layer -> commit what moved. Flightradar24 keeps a
    flight's trail about four days, so the job has to run at least weekly; twice a day loses nothing.
    Still yours by hand: FR24 app screenshots and timetable captures (the workflow warns when they
    lag), the FTA board crawl, and closing a month (Actions -> Run workflow -> close_month = 2026-10).
